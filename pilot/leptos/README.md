# Leptos WASM pilot

A tiny, standalone [Leptos](https://leptos.dev/) client-side-rendered app compiled to
WebAssembly and loaded directly by a browser. It exists purely as a feasibility
experiment: a self-contained page that proves a Leptos UI can build for
`wasm32-unknown-unknown`, bind to JavaScript with `wasm-bindgen`, and render into a
plain HTML shell — no bundler, framework CLI (trunk/cargo-leptos), or backend required
to view it.

## Layout

```
pilot/leptos/
├── Cargo.toml        # the `pm_leptos_pilot` cdylib crate (added alongside this pilot)
├── build.sh          # builds + wasm-bindgen + stages artifacts into web/
├── web/
│   ├── index.html    # static HTML shell, inline dark-theme CSS, boot script
│   ├── pm_leptos_pilot.js      # generated by wasm-bindgen (staged by build.sh)
│   ├── pm_leptos_pilot_bg.wasm # generated by wasm-bindgen (staged by build.sh)
│   └── pkg/          # raw wasm-bindgen output (build artifacts)
└── README.md
```

`index.html` contains a `<div id="root"></div>` that the Leptos app mounts into,
plus a small inline module that calls the generated `init()` function. With
`wasm-bindgen --target web`, importing `pm_leptos_pilot.js` alone is not enough —
its default export (`init`) must be called to instantiate the WASM. Called with no
arguments, `init()` finds `pm_leptos_pilot_bg.wasm` next to the JS file via
`import.meta.url`, which is why `build.sh` copies both artifacts into `web/`.

## Prerequisites

Install these once, before running `build.sh`:

1. **WASM target** (via rustup, not Cargo):

   ```sh
   rustup target add wasm32-unknown-unknown
   ```

2. **wasm-bindgen CLI, version `0.2.130`** — must match the `wasm-bindgen` crate
   version resolved in `Cargo.lock`:

   ```sh
   cargo install wasm-bindgen-cli --version 0.2.130
   ```

`build.sh` checks for both and fails with a helpful message if they are missing;
it does not install anything on its own.

## Build

From this directory (`pilot/leptos/`):

```sh
./build.sh
```

This runs `cargo build --release --target wasm32-unknown-unknown`, feeds the
resulting `pm_leptos_pilot.wasm` to `wasm-bindgen --target web`, and copies the
generated `.js` and `_bg.wasm` into `web/`. Re-run it after any Rust change.

## Serve

The page must be served over HTTP (ES module imports do not work from `file://`).
Any static server works; with Python:

```sh
python3 -m http.server 8080 -d web
```

Then open <http://localhost:8080/>. Serve with a different port by changing `8080`.

## What this pilot demonstrates

- Building a Leptos CSR app for the `wasm32-unknown-unknown` target.
- Binding it to the browser with `wasm-bindgen --target web` (no bundler).
- Loading the generated ES module from a hand-written HTML shell with inline,
  dependency-free CSS (no CDN, no external assets).
- A minimal reactive UI rendered into `#root` as a visual smoke test.

## What this pilot does NOT replace

- It is **not** the production Portmaster UI. The shipped interface remains the
  Angular app under `desktop/angular` (packaged with Tauri under `desktop/tauri`).
- It has **no backend**: it does not talk to the daemon, use pm-api, or display any
  real connection/profile/intel data. Anything on screen is local demo state.
- It lacks the production UI's routing, i18n, theming, settings persistence,
  desktop integration, and accessibility work.
- It is a throwaway feasibility harness, not a migration plan or a drop-in
  component. Reuse of it would need a real build/serving story (e.g. trunk or
  cargo-leptos), backend integration, and a full design/i18n pass.
